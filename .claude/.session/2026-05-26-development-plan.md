# 2026-05-26 · 开发任务拆解

> **议题**:基于 architecture.md 的渐进式开发任务拆解
> **结论**:产出 [`docs/development-plan.md`](../../docs/development-plan.md),22 个任务分 7 阶段,每个含功能/验收/验证方式三段式。

---

## 关键设计选择

### 1. 拆解粒度
- 每个任务约 0.5-1 天工作量
- 每个任务必须**独立可验证**(curl / typecheck / 浏览器三选一)
- 验证方式尽量给可直接执行的命令片段,不留模糊地带

### 2. 阶段顺序权衡
- 后端 Phase 2 与前端 Phase 3 从 T0.2 起可**并行**
- AI 拆解放在 Phase 5 而非靠前:前 4 阶段不依赖 AI,即使 DeepSeek 接口延迟也不阻塞主线
- 日历晚于看板:看板里的"安排"按钮是日历的入口,先有按钮再有目的地

### 3. 几个特别的设计
- **T1.2 起埋调试端点 `/api/_debug/*`**,Phase 7 收尾统一删除——开发期省去手测痛点
- **T2.3 把"步骤全勾完自动转 completed"放在后端**而非前端,确保不论从哪个客户端改步骤状态都一致
- **T2.4 overdue 不入库**,运行时派生(对齐 architecture §6.2),避免持久化时间敏感字段
- **T3.3 加了 bundle 检查**:确保前端 `import type { AppType }` 不会把 server 代码打进 bundle
- **T5.3 拆解失败后不删除 draft**,允许用户手动加步骤,降低 AI 不稳定的风险

### 4. 测试基线(刻意宽松)
- 单人项目,不强制 100% 单测覆盖
- 必测项只有:shared schema、deriveStatus、≥30 行的纯函数
- 接口 / UI 行为以 curl + 浏览器为准,验收命令固化进文档

### 5. 完成度自检
- 文档末尾给了 6 条检查项,直接对齐 PRD §2-§6 + 附录 A
- 所有"不做"项也要求确认未做(防止 scope 蔓延)
